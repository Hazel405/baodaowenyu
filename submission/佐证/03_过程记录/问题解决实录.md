## 实录 01 · 地名简繁归一失效（2026-10-06）

**发现渠道**：通读检索层代码时发现对照表规模异常。

**问题现象**
`server/rag_server.py` 的简繁转换对照表只有 **19 个汉字**（`兰台莲花东云梦县里斗阿崇庄处乡号湾极与`）。
而库内 31,998 条地名别名使用的汉字达 **2,640 种**——意味着绝大多数简体输入根本无法还原为库内繁体写法。

**定位依据**
1. 逐条统计 `tw.gaz_alias` / `tw.gaz_tw` / `tw.boundary` 全部地名用字 → 2,640 种；
2. 用 OpenCC 正查逐字评估原表覆盖率 → 正确覆盖 **13 字（1.6%）**，漏 **803 字**，另有 **3 字映射错误**（台/里/斗）；
3. `docs/已知限制与改进项.md` 已登记该问题，但未见量化的影响面。

**关键判断：必须用词级转换，不能用单字大表**
实测库内用字分布：`里` 出现 6,380 次、`裡` 仅 63 次 → 库里「里」是**本字**；
若用单字表做简→繁，会把「后里」「万里」这类地名误转为「後裡」「萬裡」。
故采用 OpenCC 的 **`s2tw`（台湾正体）词级**转换，并保留自建表作降级兜底。

**动作**
1. `s2t()` / `t2s()` 改为 OpenCC `s2tw` / `tw2s`，缺失 OpenCC 时自动降级到内置表；
2. 内置扩展表由 19 字扩至 **709 字对**（按 OpenCC 正查 + 库内频次筛选生成，避免歧义选字错误）；
3. `extract_entities` 增加**简繁归一后去重**（见下条踩坑）；
4. 新增 `eval/measure_s2t.py` 作为可复现的量测脚本。

**踩坑与修复（过程留痕，不掩盖）**
- 改动后 QA30 首次回归 **29/30**，第 27 题「台中市和台北谁人口多？」失败。
- 定位：`s2t("台中市")` 现在返回「臺中市」，使简繁变体被当作**两个独立实体**加入 → 实体列表变 `['台中市','臺中市','台北']` → 查询翻倍 → `q_population` 的 `out[:6]` 截断把「台北」挤掉。
- 修复：实体按简繁归一后去重。
- 二次回归成功，但发现第 27 题**数字口径变化**：改进使 `alt IN ('台中市','臺中市')` 额外激活 gaz_tw 的 **ADM2 行政区条目**（2,867,848），跳出测试硬编码区间 → 同步更新期望值并注明口径。

**验证数字（三重）**

| 验证项 | 结果 |
|---|---|
| 名称还原率（31,998 条地名别名） | 30.52% → **84.55%**（+54 个百分点） |
| QA30 回归（30 题基准） | **acc = 1.0（30/30）**，基线未退化 |
| 端到端简体问句实测 | **8/8 命中**（台东/苏澳/芦洲/新庄/员山…） |

**留痕**
- 提交：`12e4f29`（见 `提交历史_含改动明细.txt`）
- 量测脚本：`eval/measure_s2t.py`（可复现）
- 截图：待补 `01_截图/06_问题修复前后/`（简体输入命中繁体库名的前后对比）
- 说明文档：`修改第二版\19_改进A_简繁归一改进说明.md`

## 实录 02 · 数据库转储缺表导致换机必坏（2026-10-04）

**问题现象**
接手包内 `data/db/tw_20261001.dump` 转储只含 71 张 `tw` 表，缺 `tw.pop_county`(22 行) / `tw.pop_town`(204 行) / `tw.cities_major`(20 行) 三张人口表。
而三处代码硬编码依赖这三张表（MVT 瓦片图层、QGIS 插件「览」面板、网页数据导出）→ 换机恢复后三个图层 500、人口层空。

**定位依据**
全项目 grep `CREATE TABLE` 只有一处（`rag_server.py` 建 `tw_demo_townpop`）——证明这三张表**无任何脚本创建**，属原机手工建库遗留。

**动作**：按合规要求重建转储（补齐 3 张表 + 剔除非民用要素表），保持原文件名以兼容 12 处文档引用，在部署说明加版本说明块。

**验证数字**：转储 51,532,142 字节 / SHA256 `ba9a4b59…`（见 `校验值.txt`）；`pg_restore -l` 核出 75 张 TABLE 项。

**留痕**：提交 `8956636`。

## 实录 05 · 「暴雨情景」查询 SQL 别名缺失（2026-10-06）

**发现渠道**：演示视频拍摄前的实操走查（镜 7 · 地形与灾害参考）。

**问题现象**
QGIS 插件「析 · 地形灾害参考」面板选择某县市后点击「暴雨情景 · 受影响聚落」，返回
`情景查询失败：missing FROM-clause entry for table "z"`，功能完全不可用。

**定位依据**
`plugin/baodao_wenyu/panels/analysis.py` 的 `scenario()` 中，SELECT 列表的 5 个字段全部带 `z.` 前缀，
而 FROM 子句写作 `FROM tw.dem_zonal_stats`——**漏写表别名 `AS z`**，PostgreSQL 无法解析限定名。
（同名 SQL 在 `zonal()` 方法中未使用别名，故「分区统计」功能始终正常，问题被长期掩盖。）

**动作**
1. `FROM tw.dem_zonal_stats` → `FROM tw.dem_zonal_stats AS z`；
2. 同步修正**两份副本**：源码 `plugin/baodao_wenyu/panels/analysis.py` 与 QGIS 安装目录
   `%APPDATA%\QGIS\QGIS3\profiles\default\python\plugins\baodao_wenyu\panels\analysis.py`（避免"改了源码没生效"的二次踩坑）；
3. 插件重载方式写入记录：QGIS → Plugins → 插件管理器 → 宝岛文舆 取消勾选再勾选。

**验证数字**：以该县市直接执行修复后 SQL，命中 1 个乡镇「仁愛鄉」——平均坡度 **27.6°**、
陡坡（>30°）占比 **43.4%**、2 级河道占比 **0.7%**、通行难度 **70**。
命中数量少属**数据覆盖缺口的如实呈现**（`tw.dem_zonal_stats` 覆盖县 21 + 乡镇 201，未覆盖部分按缺口记档），
非查询错误；该缺口提示在演示中保留展示。

**留痕**：提交 `（见提交历史最新条）`；截图：待补 `01_截图/06_问题修复前后/`（报错面板 → 修复后结果面板）。

## 实录 06 · 演示底图"白屏"：自产瓦片层级上限未文档化（2026-10-06）

**发现渠道**：演示视频拍摄实操（镜 2 · 自产底图缩放）。

**问题现象**
在 QGIS 中把视图定位到城市尺度（比例尺 1:2,000）后画面**全白**，无任何底图内容，
一度被误判为"坐标定位失败/瓦片服务宕机"。

**定位依据**
1. 检查瓦片目录：`basemap/street` 最大层级 **z13**、`basemap/terrain` 最大层级 **z12**；
2. 换算：z13 对应比例尺约 **1:6.5 万**（地面分辨率约 17 m/px）——视图比例尺小于该值即超出瓦片金字塔，**必然空白**；
3. 瓦片服务本身正常（`/` 返回 200），故排除服务故障。

**动作**
1. 演示缩放起点改为 **1:100,000**（留安全余量），外拉 4~5 档至全岛；
2. 在 `docs/演示视频分镜.md` 镜 2 行与「制作备忘」补记**瓦片层级上限与最小可用比例尺**；
3. 同批修正：镜 2 原脚本要求点击「＋注入自产底图」，而演示工程 `demo_project.qgz` 已内置「街道图 / 地形晕渲」两个 XYZ 图层，
   重复注入会叠加图层并强制跳回全岛 extent（`plugin.py:107`）→ 从脚本中删除该动作。

**验证**：按修正后流程（全岛 → 拖动手型工具定位城区 → 比例尺 1:100,000 → 外拉 5 档）实测画面连续有内容，
缩放过程为"街道级 → 地形晕渲"的自然过渡（低层级自动隐藏街道瓦片系设计行为，非缺陷）。

**留痕**：提交 `（见提交历史最新条）`；文档 `docs/演示视频分镜.md`。

## 实录 07 · 人口口径混用与「来源」标注漂移（2026-10-06 登记，待修复）

**发现渠道**：演示视频拍摄前的接口走查（逐问法实测 `/api/ask`）。

**问题现象**
同一县市人口问题会命中**两套口径**并**并列多个数字**，且答案末尾的「来源」标注与实际取值表不符。实测：

| 问法 | 返回 | 判定 |
|---|---|---|
| 某县（示例 A） | 450,031（单值） | 数字取自地理名词典 ADM2 人口，标注却写 WorldPop 分区表 → **口径不符** |
| 某县（示例 B） | 479,666（单值） | 同上 |
| 某直辖市 | 2,737,660 ＋ 2,733,964 ＋ 2,780,477（**3 个并列**） | 不可用 |
| 某市 | 362,487 ＋ 362,177 ＋ 625,476（**3 个并列**） | 不可用 |
| 全台合计 | **24,064,538**（单值，来源＝WorldPop 2020 合计） | ✅ 唯一干净问法 |

**定位依据**
`server/rag_server.py` 的 `q_population()` 对同一实体**同时**查询两路：
① `tw.gaz_tw`（GeoNames 行政区/居民点人口）；② `tw_demo_countypop`（GADM 边界 × WorldPop 2020 分区汇总）。
两路数值本不相同，输出时未定优先级即并列；且「【来源：…】」由模型自由书写，存在标注漂移。

**临时处置**：演示视频中人口问题改用「全台人口总计多少？」（单值、与报告口径一致）。

**修复方案（登记待办）**：县级人口口径固定为 `tw_demo_countypop`（与报告一致）；多路命中时不并列、取权威口径并注明口径名；
「来源」行由服务端生成后固定附加，不交模型书写；完成后跑 QA30 回归（期望 acc=1.0）＋ 上表 8 个问法固化用例。

**留痕**：`修改第二版\22_镜4录制脚本与系统缺陷记录.md`（含完整实测对照表）。

**问题现象**：QGIS 插件「询 · 地志智询」问答成功后点击「在地图上定位答案实体」，**画面无任何变化**（无报错、无跳转）。

## 实录 09 · 录制链路音频底噪处置（2026-10-06）

**问题现象**：首段录屏回放有明显"沙沙"底噪（笔记本内置麦增益偏高）。

**判定与处置**：口播按计划在后期统一录制，录制阶段的现场音轨本身不进入成片 →
① 不重录，成片阶段静音该段音轨；② 源头治理：OBS 混音器麦克风静音 + 设置→音频→麦克风与桌面音频均设为「已禁用」，
使后续镜头录制为纯画面素材，同时避免系统通知声被录入。

**留痕**：`录像\01_OBS安装与试录操作单.md`（音频处置小节）。
